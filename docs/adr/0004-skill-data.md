# ADR-0004: Skill Data Representation and Acquisition

## Status

Accepted (2026-10-23); importer implementation is Sprint 9.

## Context

The brief requires treating the original GW1 skill corpus as _reference data_
ingested through a separate pipeline, never hand-copied into TypeScript, with
full provenance, no silent data loss, and an explicit PvP/PvE distinction
(§7–§10, §45).

Two things were checked directly rather than assumed:

- **Reachability**: `wiki.guildwars.com`'s MediaWiki API was queried on
  2026-10-23 and currently returns "The Guild Wars Wikis are undergoing
  maintenance" instead of API data. This is the primary source the brief
  names first. It may well be back by Sprint 9, but the importer must not
  assume a single source is always available.
- **Licensing**: per the wiki's own `Guild Wars Wiki:Copyrighted content`
  policy, all content must be GFDL-compatible or belong to ArenaNet/NCSoft;
  critically, it explicitly treats _factual game data_ — "item stats, skills
  used, items dropped, location descriptions, skill descriptions, attribute
  descriptions, etc." — as non-copyrightable fact, distinct from the wiki's
  own prose/flavor text. This matters for us: we want the **numbers**
  (cost, recharge, range, scaling), not the wiki's written description, and
  the numbers are the part explicitly treated as uncopyrightable fact.

## Decision

- Skill data lives in its own package, **`packages/game-data`** (created in
  Sprint 9), structured as:

  ```text
  packages/game-data/
    raw/         Unmodified upstream snapshots, one subfolder per source,
                 each with a provenance file (source URL, fetch date,
                 license note).
    normalized/  Our own schema (ADR-driven, see below), one JSON file per
                 skill, hand-auditable in diffs.
    generated/   Build output consumed by the runtime; never hand-edited;
                 regenerated by the importer from normalized/.
  ```

- The importer fetches from multiple sources (Guild Wars Wiki's API when
  reachable; Guild Wars Memorial as a named alternative in the brief) and
  **never fails closed on a single source being unreachable** — each source
  is independently optional, and the importer's report names exactly which
  sources contributed which skills.
- Every imported skill is normalized into a record that explicitly carries
  `{ identity, variant (pvp|pve), ruleset, sourceVersion }` (brief §10) —
  never a bare "skill" that silently conflates PvP and PvE numbers.
- Only numeric/structural facts (cost, recharge, range, attribute scaling,
  target rules, effect composition) are captured from upstream sources.
  Flavor text/lore is not reproduced verbatim from the wiki, consistent with
  not needing or wanting GFDL prose in a build-time data file.
- Unknown/unrepresentable fields are preserved under an explicit `unmapped`
  bag in the normalized record and surfaced in the importer's coverage
  report, never silently dropped (brief §7.8, §9).
- The exact normalized-record schema (field names, effect-composition shape)
  is deferred to a dedicated ADR written _in_ Sprint 9, once real upstream
  data has been seen — writing the final schema now, against zero real
  records, would be exactly the kind of premature guess the brief tells us
  to avoid (§45: "document the uncertainty... rather than silently
  guessing"). This ADR fixes the _pipeline shape and provenance rules_ now;
  ADR-00xx (Sprint 9) fixes the _schema_.

## Consequences

- The runtime (`game-core`'s skill engine, from Sprint 10) only ever reads
  `generated/`, so the engine's input shape is decoupled from whichever
  upstream source happened to supply a given skill, and from that source's
  uptime.
- A coverage report (imported → normalized → representable → implemented →
  tested → playable, per brief §9) becomes possible to generate mechanically
  because every stage of that pipeline is a distinct, inspectable directory.
- Because the Wiki is down right now, Sprint 9 must budget time to either
  wait, use Guild Wars Memorial first, or use a cached/archived snapshot —
  this is flagged here so it is a known risk going into that sprint, not a
  surprise.

## Alternatives Considered

- **Hand-author a curated subset of skills directly as TypeScript.** Rejected
  outright by the brief (§7: "Do not manually copy thousands of skills into
  TypeScript source") and it would make "every GW1 PvP skill eventually
  represented" unreachable in practice.
- **Single source of truth (Wiki only).** Rejected after confirming it is
  presently unreachable — a single-source importer would block Sprint 9
  entirely on an upstream outage outside this project's control.
