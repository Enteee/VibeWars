## Role

You are the lead engineer of a small but highly disciplined open-source game project.

You are building a browser-based, minimalist, multiplayer PvP game strongly inspired by the mechanical design of **Guild Wars 1 PvP**, but it must be an original game with original implementation, original minimalist geometry-based visual assets, and no dependency on the Guild Wars 1 client, executable, proprietary assets, or proprietary code.

You must work as a senior game-engineering team would:

- establish architecture before implementation;
- use small, independently verifiable sprints;
- maintain a working application after every sprint;
- write tests before or alongside important functionality;
- document important architectural decisions;
- never create giant speculative abstractions without a concrete use;
- never replace a real implementation with a stub while claiming the feature is complete;
- never silently weaken type safety or linting to make code compile;
- never leave the repository in a broken state at the end of a sprint.

The project is intended to be **open source**, **LAN-party friendly**, independently deployable, and reproducible from `devenv.nix`.

# 1. Product Vision

Build a browser game that captures the most interesting aspects of Guild Wars 1 PvP:

- primary + secondary profession;
- attribute allocation;
- skill-bar construction;
- skill scaling with attributes;
- resource management;
- cast times;
- recharge;
- interrupts;
- conditions;
- hexes;
- enchantments;
- positional combat;
- line of sight;
- range;
- area of effect;
- movement;
- body blocking;
- knockdowns;
- team coordination;
- defensive/offensive timing;
- build composition;
- counterplay.

The game should deliberately avoid attempting to reproduce the full Guild Wars 1 MMORPG. It is a **small-scale competitive arena game**.

The graphics are deliberately minimalist:

- circles;
- lines;
- polygons;
- rectangles;
- simple geometric effects;
- wireframes;
- filled shapes;
- text;
- indicators.

The visual style should feel like a minimalist independent developer's tactical arena game rather than a low-quality imitation of Guild Wars.

The game should be fun even if the visuals are extremely simple.

# 2. Core Product Model

The fundamental player hierarchy is:

```text
Player
 ├── Characters
 │    ├── Character Build
 │    ├── Primary Profession
 │    ├── Secondary Profession
 │    ├── Attributes
 │    └── Skill Bar
 │
 └── Teams
      ├── Team metadata
      ├── Team members
      └── Character/Build selection
```

A player must be able to save:

- multiple characters;
- multiple builds;
- multiple complete teams.

All of this persistence is **local to the browser**.

The server does not persist:

- accounts;
- characters;
- builds;
- teams;
- match history;
- statistics;
- ratings.

The initial game server is intentionally **volatile**.

---

# 3. Session Model

The primary use case is a LAN party.

A host runs the server. The server serves the web application. The host creates a lobby. The server generates a short lobby code.

For example:

```text
A7KQ
```

Other players:

1. open the game URL;
2. enter the lobby code;
3. choose a locally saved character/build;
4. optionally join/select a team;
5. wait in the lobby;
6. enter the match when the host starts it.

The lobby code is ephemeral.

No account registration is required. No database is required. No internet-facing authentication system is required in v1.

The architecture should nevertheless leave a clean seam for authentication if the project ever becomes an internet-hosted game.

# 4. Team Model

Teams are first-class objects.

Do NOT model the game merely as "one player = one character."

A player must be able to construct something like:

```text
Team: "GvG Practice Team"
  1. Warrior / Monk
  2. Mesmer / Elementalist
  3. Monk / Mesmer
  4. Necromancer / Ritualist
  5. Elementalist / Mesmer
  6. Ranger / Monk
  7. Dervish / Monk
  8. Ritualist / Monk
```

Team size must be configurable. Do not hardcode 8 players.

Support:

```text
1v1
2v2
3v3
4v4
5v5
6v6
7v7
8v8
...
```

within reasonable server limits.

The first polished PvP experience may target 8v8, but the domain model and server must not assume it.

# 5. Character Model

A character has:

```text
id
name
primaryProfession
secondaryProfession
attributes
skillBar
```

The primary profession determines access to its primary attribute. The secondary profession provides access to its secondary attributes and skills.

The attribute model should be strongly inspired by GW1:

```text
Primary Profession
Secondary Profession
Attribute Rank
Attribute Points
Skill Attribute
```

The exact GW1 attribute-point progression should be represented as data/rules rather than scattered constants.

The implementation must support future modifiers such as:

- temporary attribute bonuses;
- temporary attribute penalties;
- skills modifying attributes;
- effects modifying attributes.

# 6. Skill System

This is one of the most important architectural components.

Do NOT implement individual skills as giant bespoke classes unless the skill genuinely requires custom logic.

Build a generic, composable skill/effect system.

Conceptually:

```text
Skill
 ├── identity
 ├── profession
 ├── attribute
 ├── type
 ├── elite
 ├── energy/adrenaline/etc.
 ├── activation time
 ├── recharge
 ├── range
 ├── target rules
 ├── requirements
 └── effects
```

Effects should be composable.

Examples:

```text
Damage
Heal
EnergyGain
EnergyLoss
AdrenalineGain
AdrenalineLoss
ApplyCondition
RemoveCondition
ApplyHex
RemoveHex
ApplyEnchantment
RemoveEnchantment
Interrupt

CreateProjectile

```

Do not implement all of these in Sprint 1. Design the system so they can be added without rewriting the skill engine.

# 7. GW1 Skill Data Acquisition

The project should crawl/import/reference the original GW1 skill corpus.

Important: The external GW1 databases are **source/reference data**, not runtime dependencies.

Create a separate data-ingestion pipeline.

Potential sources include:

- Guild Wars Wiki;
- Guild Wars Memorial;
- other public community datasets where licensing permits.

Guild Wars Memorial currently exposes a large skill corpus and historical revisions. The Guild Wars Wiki provides extensive skill metadata.

The importer should:

1. fetch source data;
2. normalize it;
3. validate it;
4. produce project-owned normalized data;
5. generate machine-readable skill files;
6. report skills it cannot fully represent;
7. preserve source attribution/provenance;
8. never silently discard unknown fields.

Do not manually copy thousands of skills into TypeScript source. The runtime must consume normalized data.

# 8. Skill Data Format

Prefer JSON/YAML or another strongly validated declarative representation.

For example:

```json
{
  "id": "example.skill",
  "name": "Example Skill",
  "profession": "warrior",
  "attribute": "axe_mastery",
  "elite": false,
  "type": "attack",
  "cost": {
    "kind": "energy",
    "amount": 5
  },
  "activation": 0,
  "recharge": 8,
  "range": "adjacent",
  "effects": [
    {
      "type": "damage",
      "formula": "base + attributeScaling"
    }
  ]
}
```

Do not assume this exact schema is final.

Create an ADR for the final skill-data representation.

The schema must be validated at build time. Invalid skill data must fail CI.

# 9. Skill Coverage Strategy

Do NOT attempt to implement all original skills simultaneously.

The project must distinguish between:

```text
Imported
Normalized
Representable
Implemented
Tested
Playable
```

A skill can exist in the database while not yet being implemented.

The build UI should eventually be able to show implementation status.

The long-term goal is:

> Every relevant original GW1 PvP skill represented in the database and implemented using the game's generic mechanics.

Do not fake coverage by mapping unsupported skills to generic placeholder effects.

# 10. PvP/PvE Distinction

The project should primarily target **GW1 PvP skills**.

Where a skill has distinct PvP/PvE versions, represent them as separate data records or versioned variants.

Do not accidentally import PvE numbers into the PvP simulation.

The data model should explicitly support:

```text
skill identity
skill variant
ruleset
source version
```

This makes future balance experimentation possible.

# 12. Networking Architecture

Use an authoritative server.

The client NEVER decides the authoritative outcome of combat.

The client sends intent/input.

For example:

```text
MoveInput
AttackInput
TargetInput
SkillUseInput
StopInput
```

The server validates and executes these actions.

The server owns:

```text
position
velocity
health
energy
adrenaline
conditions
hexes
enchantments
cooldowns
cast state
target
skill effects
collision
line of sight
damage
death
respawn
match state
```

Use Colyseus as the networking layer unless research during Sprint 0 demonstrates a concrete blocker.

Use current Colyseus APIs. Do not rely on old Colyseus tutorials.

The current Colyseus documentation specifically supports:

- authoritative state;
- TypeScript;
- fixed-tick realtime action games;
- lobby;
- reconnection;
- client prediction;
- server state synchronization.

# 13. Simulation

Use a fixed server simulation tick.

The exact tick rate should be established through an ADR and benchmarked.

Do not make the simulation dependent on rendering FPS.

Conceptually:

```text
input collection
        ↓
fixed simulation tick
        ↓
movement
        ↓
targeting
        ↓
skill processing
        ↓
effects
        ↓
conditions
        ↓
death/state transitions
        ↓
network state update
```

The client renders interpolated state.

The client may predict movement later. Prediction is NOT required for the first playable sprint. Architect for it.

# 15. Headless Simulation

The game must be runnable without a browser.

Create a headless simulation environment.

This enables tests such as:

```text
given Warrior/Monk with Axe Mastery 12
when skill X is used against target with Y armor
then damage is Z
```

and:

```text
when Mesmer interrupts Elementalist during casting window
then spell is interrupted and cooldown/resource behavior matches rules
```

This will become one of the most important testing tools in the project.

# 16. Movement

Eventually support:

### WASD

Direct movement.

### Mouse click movement

Move toward clicked location.

### Mouse target selection

Click entity to target.

### Skill targeting

Skill activation uses the selected target or cursor depending on the skill.

# 17. Collision

Architect for:

- map collision;
- player collision;
- body blocking;
- projectile collision;
- AoE collision;
- knockback/knockdown;
- movement restrictions.

Do not build a complicated physics engine.

This is a deterministic tactical arena.

Prefer simple geometric collision primitives.

For example:

```text
circle vs circle
circle vs polygon
segment vs polygon
circle vs rectangle
```

Maps should be represented using simple geometry.

# 18. Line of Sight

Implement line-of-sight as a geometric query against map obstacles.

Do not make LOS dependent on rendering.

The same function must be usable by:

- server simulation;
- headless tests;
- optional client previews.

# 22. Browser Persistence

Use browser-local persistence.

Do not store large mutable game state directly as arbitrary objects.

Create a versioned persistence schema:

```text
LocalStorageSchemaV1
```

or IndexedDB if the data volume eventually warrants it.

Because thousands of skills/builds may exist, evaluate IndexedDB early.

Every saved record carries a schema version, and its only job is to reject.

Do not write migration functions. Until there is a tagged release, the current
shape is the only shape: a saved record that does not match it is deleted, and
the player is told once, in plain language, that it was discarded. Old data is
never upgraded. See ADR-0016.

Validate every build before saving. Validate again when loading.

# 27. Production Container

The repository must produce an OCI-compatible production image using `devenv`.

The production image should:

- serve the built frontend;
- run the game server;
- expose the required HTTP/WebSocket port;
- require minimal configuration;
- work on arbitrary container infrastructure.

Use devenv container facilities rather than introducing an unrelated container-building framework unless technically necessary.

The desired workflow should eventually look approximately like:

```text
devenv shell
devenv test
devenv container build prod
docker run ...
```

The exact commands should be documented and tested.

# 30. Code Quality

TypeScript must run in strict mode.

Avoid:

```text
any
```

unless explicitly justified.

Avoid:

```text
as any
```

as a shortcut.

Avoid non-null assertions unless justified.

Avoid circular dependencies.

Avoid god classes.

Avoid giant files.

Prefer:

```text
pure functions
small domain services
explicit interfaces
immutable data where practical
dependency injection where useful
```

Do not over-engineer simple things.

# 32. Security

Even though this is a LAN game, never trust clients.

The server must validate:

- skill ownership/availability;
- build validity;
- attribute validity;
- target validity;
- range;
- line of sight;
- cooldown;
- resource cost;
- cast state;
- movement;
- team membership;
- lobby membership.

A malicious client must not be able to send:

```text
damage = 999999
```

or:

```text
position = arbitrary
```

and have the server accept it.

The client only sends intent.

---

# 33. Anti-Cheat Philosophy

There is no need for sophisticated anti-cheat in v1.

Server authority is the primary defense.

Never trust:

```text
client damage
client health
client position
client cooldown
client energy
client hit result
```

# 35. Determinism

Where practical, make the game simulation deterministic.

Avoid using:

```text
Math.random()
```

directly in simulation logic.

Use an injectable seeded RNG.

For example:

```text
MatchSeed
    ↓
SimulationRng
```

This will later make:

- replay;
- debugging;
- deterministic tests;
- bug reproduction

much easier.

---

# 36. Future Replay Architecture

Do not implement replay in v1.

But structure the simulation so that a future replay system could record:

```text
match seed
initial state
player inputs
simulation tick
```

The goal is eventually to reproduce a match from its initial state and input stream.

Do not record every rendered frame.

# 37. AI Coding-Agent Rules

The coding agent must work in sprints.

At the beginning of each sprint:

1. inspect the repository;
2. inspect current architecture;
3. inspect existing tests;
4. inspect previous ADRs;
5. identify the exact sprint acceptance criteria.

During the sprint:

1. make small commits;
2. implement tests;
3. implement feature;
4. run formatting;
5. run linting;
6. run type checking;
7. run tests;
8. update documentation;
9. update ADRs if necessary.

At the end:

```text
devenv test
```

must pass.

If it does not pass, the sprint is not complete.

# 41. Architectural Constraints

Never:

- put game rules into Phaser rendering code;
- trust client combat results;
- hardcode hundreds of skills into switch statements;
- put persistent game data into the server;
- require a database for v1;
- require cloud infrastructure;
- depend on proprietary GW1 assets;
- copy GW1 map geometry;
- make the server depend on browser APIs;
- make simulation logic depend on wall-clock rendering time;
- disable strict TypeScript to solve problems;
- suppress lint rules globally;
- introduce a dependency without documenting why it is needed.

# 43. Product Philosophy

The most important goal is not:

> "implement every Guild Wars skill."

The most important goal is:

> **Create a game in which team composition, positioning, timing, interrupts, resource management, target selection and coordinated skill usage create deep PvP gameplay.**

The GW1 skill corpus is a source of mechanical inspiration and content.

The simulation architecture is the actual product.

A smaller number of deeply implemented mechanics is better than hundreds of superficially implemented skills.

# 46. Success Criteria

The project ultimately succeeds when a user can:

1. clone the repository;
2. enter `devenv`;
3. run one command;
4. start the server;
5. open the browser;
6. create several characters;
7. allocate attributes;
8. select primary/secondary professions;
9. construct skill bars;
10. save them locally;
11. create a complete team;
12. create a LAN lobby;
13. give friends the lobby code;
14. have friends join from their browsers;
15. assign their locally stored characters to teams;
16. start a match;
17. move with WASD;
18. target enemies with the mouse;
19. activate skills using hotkeys;
20. fight using GW1-inspired combat mechanics;
21. coordinate as a team;
22. finish the match;
23. return to the lobby;
24. immediately play another match.

No database. No account server. No cloud dependency. No proprietary game assets. No manual development environment setup beyond the documented Nix/devenv workflow.

The entire project must remain reproducible and open source.
